# Telegram-интеграция Бибибайка

Этот документ описывает путь пользователя от публичного сообщества до получения бибибонусов, обязательные настройки Telegram и проверку на Android, iOS и Desktop.

## Компоненты

- Публичная группа: [@bbbikefan](https://t.me/bbbikefan).
- Бот: [@BbGalterbot](https://t.me/BbGalterbot).
- Mini App short name: `bibibike`.
- Прямая ссылка Mini App: `https://t.me/BbGalterbot/bibibike`.

## Обязательный brand gate перед пилотом

Публичный запуск запрещён, пока карточки Telegram показывают старые или
несвязанные названия. В BotFather и настройках группы нужно проверить одним
новым аккаунтом:

- бот отображается как `БибиЗадачи · Бибибайк` с утверждённым зелёным логотипом;
- публичная группа явно называется сообществом Бибибайка и использует тот же
  визуальный стиль;
- описание бота объясняет задания и бибибонусы, описание группы содержит ссылку
  на `@BbGalterbot`, а закреплённое сообщение ведёт в Mini App;
- ни одна карточка не использует старые названия `Зеленый велосипед`,
  `BibiПомощник` или постороннее англоязычное описание.

Проверка выполняется по публичным ссылкам в режиме инкогнито/с нового аккаунта,
а не только из учётной записи владельца, где Telegram может показывать кэш.
- Рабочий backend: проверяет Telegram `initData`, хранит участников, задания, доказательства и журнал бонусов.

## Минимальная связка

Минимальный вариант сохраняет одну публичную группу и long polling:

```text
Реферальная ссылка
  -> личный чат с @BbGalterbot
  -> вступление в @bbbikefan
  -> Mini App
  -> анкета: имя, город, чем человек полезен
  -> ручное одобрение
  -> задание в теме «Работа» и Mini App
  -> фото результата в Mini App
  -> проверка ответственным
  -> одна проводка бибибонусов
```

Реферальная ссылка должна содержать непрозрачный случайный token, а не Telegram ID:

```text
https://t.me/BbGalterbot?start=rf_<token>
```

Параметр `start` следует держать не длиннее 64 base64url-символов. Сервер хранит hash token, referrer, срок действия и пользователя, который его использовал. Повторный переход не должен менять уже установленного referrer.

После `/start` бот показывает две кнопки:

1. `Вступить в сообщество` -> `https://t.me/bbbikefan`.
2. `Открыть БибиЗадачи` -> `https://t.me/BbGalterbot/bibibike`.

Членство подтверждается событием `chat_member`, а `getChatMember` используется для повторной проверки. `new_chat_members` можно оставить только для приветствия.

Задание открывается по ссылке:

```text
https://t.me/BbGalterbot/bibibike?startapp=task_<id>
```

`task_<id>` — только навигация к карточке, а не разрешение. Backend отдельно
проверяет подписанный Telegram initData, пользователя, роль, город, время и
состояние задания. ID задания не содержит персональных данных и не даёт доступа
к закрытому заданию.

## Целевая профессиональная связка

В v2.6 исходящие критические сообщения уже ставятся в SQLite outbox в той же
транзакции, что изменение задания или баланса. Worker повторяет доставку с
backoff, после десяти ошибок помечает событие `dead`, а `/health` сигнализирует
об этом. Для нескольких экземпляров этот механизм переносится в PostgreSQL;
входящие Telegram updates дополнительно требуют webhook secret и durable inbox.

В целевом варианте публичное сообщество и рабочая зона разделены:

```text
Публичная @bbbikefan
  -> @BbGalterbot
  -> подписанный referral flow
  -> Mini App /bibibike
  -> анкета и одобрение
  -> приватная ops-supergroup
  -> карточка задания с исходным фото
  -> claim
  -> proof «до/после»
  -> независимая проверка
  -> идемпотентная проводка
  -> уведомление и кошелёк
```

Публичная группа используется для новостей, знакомства и инструкций. Адреса, персональные задания и доказательства размещаются в отдельной приватной supergroup с темами:

- `Задания`;
- `Проверка`;
- `Команда`.

Для прямого входа нового пользователя допустима ссылка:

```text
https://t.me/BbGalterbot/bibibike?startapp=rf_<token>
```

Telegram передаёт значение в подписанном поле `start_param` внутри `initData` и также в непроверенном GET-параметре `tgWebAppStartParam`. Backend доверяет только `start_param` после полной HMAC-проверки `initData` и проверки `auth_date`.

Если direct Mini App ещё не получил право писать пользователю, приложение вызывает `requestWriteAccess` либо предлагает открыть личный чат бота.

### Вступление и join requests

Для управляемого набора бот создаёт собственную invite link с `creates_join_request=True`. В `chat_join_request` сохраняются пользователь, использованная ссылка, referral и время. Бот получает это событие только с правом `can_invite_users`.

Поддержку нового `sendChatJoinRequestWebApp` следует включать только после проверки установленной версии aiogram и всех целевых Telegram-клиентов. Базовый approve/decline через Bot API остаётся запасным вариантом.

### Публикация задания

После commit в БД создаётся outbox-event. Отдельный обработчик вызывает
`sendPhoto` в теме `Задания`; интерфейс скаута показывает `в очереди`,
`доставлено` или `ошибка` и разрешает повторить только окончательно упавшую
доставку.

Карточка содержит город, адрес, временной слот, награду, исходное фото и кнопку
`Открыть задание` со ссылкой `startapp=task_<id>`. Она отправляется только в
настроенную приватную `OPS_GROUP_ID` (username допустим только при локальной
разработке), никогда не в
публичный community chat.

Telegram-вызов не должен находиться внутри транзакции баланса или задания: сначала commit, затем повторяемая доставка из outbox.

### Доказательство

Предпочтительный proof загружается через Mini App и привязывается к конкретному assignment:

- фото «до» и «после»;
- комментарий;
- серверное время;
- при согласии пользователя координаты;
- ID или количество байков;
- SHA-256 локального файла;
- Telegram `file_id` и `file_unique_id` после публикации;
- `chat_id`, topic и message ID proof-сообщения.

Backend публикует proof в теме `Проверка` ответом на карточку задания. Если пользователь отправляет фото непосредственно в Telegram, оно принимается только как reply на карточку либо с одноразовым `PF-<token>`, от назначенного исполнителя и в правильной теме.

Защита от повторов строится на уникальных `update_id`, `request_id`, `(task_id, user_id)`, `(chat_id, message_id)`, review operation ID и ledger operation ID. `file_unique_id` используется как сигнал повторной отправки, а не как единственное доказательство мошенничества.

### Проверка и бонус

- Создатель или исполнитель задания не может быть проверяющим.
- Повторный callback или POST возвращает прежний результат.
- Ledger содержит `operation_id UNIQUE`.
- Ошибка Telegram после commit не отменяет начисление: уведомление повторяется из outbox.
- Исправление операции делается обратной проводкой, а не удалением истории.

## Настройки BotFather

Владелец должен вручную проверить:

- имя бота: `БибиЗадачи · Бибибайк`;
- username: `@BbGalterbot`;
- актуальные avatar, description и short description;
- команды через `/setcommands`: `start`, `tasks`, `profile`, `balance`, `instruction`, `help`;
- `/setmenubutton`: текст `Открыть задания`, production HTTPS URL Mini App;
- `Configure Mini App`: short name `bibibike`, production HTTPS URL, иконка и loading colors;
- `Main Mini App`: включён, добавлены скриншоты или видео для профиля;
- добавление бота в группы разрешено;
- privacy mode оставлен включённым, пока бот является администратором нужных групп;
- inline mode и attachment menu не включены без отдельной необходимости.

Токен бота хранится только в secret environment хостинга. После подозрения на утечку владелец немедленно перевыпускает token в BotFather и обновляет secret.

## Настройки групп и права бота

### Публичная `@bbbikefan`

- Тип: public supergroup.
- Название: `Бибибайк | Сообщество помощников`.
- Описание: `Помогаем Бибибайку в своём городе и получаем бибибонусы на поездки. Задания: @BbGalterbot → «Открыть задания». 1 бонус = 1 ₽, минута — 8,5 ₽.`
- Forum topics: включены.
- Сохранены числовой `chat_id` и реальные `message_thread_id`.
- Бот назначен администратором, не анонимным.
- Права:
  - `can_delete_messages`;
  - `can_invite_users`;
  - `can_pin_messages`;
  - `can_manage_topics` только если бот создаёт или переименовывает темы.

### Приватная рабочая группа

- Тип: private supergroup с forum topics.
- Права бота:
  - отправка сообщений и фотографий;
  - `can_delete_messages`;
  - `can_invite_users`;
  - `can_pin_messages`;
  - `can_manage_topics`.

Не выдавать боту `can_promote_members`, а также изменение информации группы без реальной необходимости.

Production preflight требует webhook, administrator с `is_anonymous=false` в
обеих группах и все перечисленные права. Он вызывает только методы `get*`:
проверяет forum mode, настроенные topic IDs и права доставки, но не отправляет,
не закрепляет и не удаляет тестовые сообщения. Telegram Bot API не имеет
read-only метода получения темы по `message_thread_id`, поэтому существование
каждой темы окончательно подтверждается в управляемой live-приёмке.

Для polling или webhook явно запросить update types:

```text
message
callback_query
chat_member
chat_join_request
my_chat_member
```

`chat_member` не входит в стандартный набор updates и должен быть указан явно.

## Privacy

- Не публиковать в публичной группе лица, номера автомобилей, персональные маршруты и точные рабочие адреса без необходимости.
- Proof и персональные задания хранить в приватной группе и авторизованном файловом хранилище.
- Публичный `/task-photo/{filename}` заменить авторизованной либо короткоживущей signed URL.
- Изображения перекодировать на сервере, удалять EXIF, ограничивать размер файла и пикселей.
- Геолокацию запрашивать только после понятного согласия.
- Окно открытия спора — 30 дней. Фото, точный адрес и операционные комментарии
  автоматически удаляются ещё через 90 дней либо через 90 дней после более
  позднего решения спора; точный контракт находится в
  [`PRIVACY-AND-RETENTION.md`](PRIVACY-AND-RETENTION.md).
- Raw Telegram `initData`, bot token и полные referral tokens не писать в логи.
- `protect_content` уменьшает обычное пересылание, но не защищает от скриншота.

## Отказоустойчивость

Минимально допускается один long-polling процесс с мониторингом. Целевой вариант использует:

- HTTPS webhook;
- `secret_token` и проверку `X-Telegram-Bot-Api-Secret-Token`;
- durable queue до ответа `2xx`;
- дедупликацию по `update_id`;
- outbox исходящих сообщений;
- обработку Telegram `429 retry_after`;
- мониторинг `pending_update_count` и последней webhook error;
- деплой без `drop_pending_updates=True`.

Сообщения в одну группу ставятся в очередь с учётом лимитов Telegram.

### Реализованный webhook-режим

Локальная разработка использует `TELEGRAM_UPDATE_MODE=polling`. Production
задаёт `TELEGRAM_UPDATE_MODE=webhook`, `PUBLIC_BASE_URL`, независимые
`WEBHOOK_ROUTE_ID`, `WEBHOOK_SECRET`, `HEALTH_TOKEN` и Fernet-ключ
`TELEGRAM_INBOX_KEY`. Итоговый маршрут имеет вид
`/telegram/webhook/<route-id>`; route ID, secret и query string не должны
попадать в access logs.

Reverse proxy обязан передавать исходный заголовок
`X-Telegram-Bot-Api-Secret-Token`, принимать только `POST` по точному маршруту,
не делать redirect и ограничивать body одним мегабайтом. После старта сервис
вызывает `setWebhook` с явным списком update types и проверяет URL,
`max_connections`, список updates и свежую ошибку через `getWebhookInfo`.
`drop_pending_updates=false` зафиксирован в коде и не управляется окружением.

До ответа `2xx` update валидируется моделью Telegram, шифруется и записывается в
`telegram_update_inbox` с уникальным `update_id` и HMAC-отпечатком. Отдельный
worker забирает запись с lease и обрабатывает её с retry; после успеха payload
удаляется, а дедупликационная запись хранится 30 дней. У dead-записи зашифрованный
payload удаляется через 7 дней. `telegram_inbox_dead>0` считается деградацией и
требует разбора, но readiness выключается только при старой активной очереди.
Повторная обработка dead update выполняется ответственным через
`POST /api/admin/telegram-inbox/redrive` с уникальным `operation_id` и причиной.
Обычный shutdown webhook не удаляет:
Telegram сохранит updates до восстановления сервиса. При переходе к polling
приложение вызывает `deleteWebhook(drop_pending_updates=false)`.

Подробный `/health/ready` требует заголовок `X-Health-Token`; публичный
`/health/live` не раскрывает состояние БД и очередей. Доставка update имеет
семантику at-least-once: изменения состояния чата дедуплицируются по `update_id`,
но Telegram-сообщение теоретически может повториться при аварии между отправкой
и фиксацией завершения inbox.

## Что владелец настраивает вручную

1. Подтверждает BotFather-настройки, production URL и Main Mini App.
2. Назначает бота неанонимным администратором обеих групп с минимальными правами.
3. Включает topics, создаёт нужные темы и передаёт разработчику числовые chat/topic IDs.
4. Оставляет `@bbbikefan` только публичным сообществом: точные адреса и proof туда не публикуются.
5. Задаёт числовой `GROUP_ID` публичной группы, создаёт приватную рабочую группу
   и задаёт отличающийся `OPS_GROUP_ID` и `OPS_TOPIC_TASKS`; production не
   запускается без обоих ID.
6. Проверяет, что invite link для join requests создан именно ботом.
7. Настраивает production secrets: bot token, admin allowlist, group IDs, webhook secret.
8. Определяет правила хранения proof, геолокации и доступа старших скаутов.
9. Назначает второго проверяющего для крупных начислений и переводов.
10. Участвует в приёмке на реальных Android, iPhone и Telegram Desktop.

## Критерии готовности

Минимальная интеграция готова, когда бот при старте проверяет свои права, получает `chat_member`, referral нельзя заменить или засчитать дважды, task/proof/review связаны через assignment, proof содержит фото, двойной claim и approve протестированы, а Telegram-сбой не теряет задание или начисление.

Целевая интеграция дополнительно требует приватной ops-группы, join requests, webhook secret, update deduplication, durable queue/outbox, независимого checker и ежедневной сверки ledger.
