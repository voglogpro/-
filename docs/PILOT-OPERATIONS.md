# Операционный регламент пилота

## Перед запуском

1. Настроить минимум двух ответственных в `ADMIN_IDS`.
2. Сгенерировать и сохранить в secret environment независимые
   `WITHDRAW_ACCOUNT_KEY`, `TELEGRAM_INBOX_KEY`, `ANALYTICS_SECRET` и
   `HEALTH_TOKEN`.
3. С заголовком `X-Health-Token` убедиться, что `/health/ready` возвращает `200`, `outbox_dead=0`,
   `telegram_inbox_dead=0`, `telegram_receiver_ready=true` и
   оба признака encryption readiness равны `true`. `/health/live` должен оставаться зелёным
   при кратком сбое Telegram, чтобы контейнер не попал в restart loop.
4. Выполнить `scripts/backup.py`, затем `scripts/restore.py` в новый каталог и,
   для S3, в отдельный пустой bucket/prefix. Сверить `restore-report.json`.
5. Выполнить тестовый цикл вторым аккаунтом: заявка → задание → фото → решение
   → бонусы → перевод → внешний номер операции.

## Перевод бонусов

Регистрация не запрашивает телефон. При создании перевода участник отдельно
вводит ID аккаунта Бибибайка. В списках видна только маска. Ответственный:

1. один назначенный на день кассир нажимает «Провести перевод» — заявка
   закрепляется за ним;
2. сверяет расшифрованный ID во внешней системе;
3. выполняет перевод;
4. вводит полученный внешний номер операции;
5. подтверждает заявку.

Нельзя подтверждать собственную заявку. Старую заявку без зашифрованного ID
можно только отклонить с возвратом. Один внешний номер нельзя использовать дважды.
Номер сравнивается без учёта регистра и Unicode-вариантов.

Пока у Бибибайка нет подключённого серверного API, внешний перевод и запись в
БибиЗадачах не являются одной атомарной операцией. Если экран закрылся после
перевода, нельзя переводить повторно: сначала найти в системе Бибибайка заявку
по `#request_id` и ID получателя, затем записать уже существующий номер операции.
В конце дня кассир сверяет все заявки `processing`; зависшие заявки передаются
следующей смене кнопкой `Передать смене` и обязательной причиной. Если
ответственный пропал, другой администратор может забрать заявку только после
тайм-аута `WITHDRAW_PROCESSING_LEASE_MIN`; takeover и release пишутся в
`withdrawal_events`.

Карточка показывает имя текущего кассира и серверный lease countdown. Повторное
раскрытие ID своим кассиром продлевает lease и пишет событие
`processing_renewed`. Отсутствующая или повреждённая старая временная метка
считается истёкшей, а не продлевается при каждой попытке takeover. Перед
`Передать смене` кассир обязан убедиться, что внешний перевод ещё не выполнен.

## Задания

- Отказ возможен только в состоянии `claimed`, до фотоотчёта.
- Отмена задания запрещена, пока существует отчёт `review`.
- После дедлайна новые взятия закрываются, `claimed` истекают, `review` остаются
  решаемыми.
- Возврат просроченного отчёта требует нового срока. Окончательное отклонение
  не начисляет бонусы.
- Создатель задания и исполнитель не подтверждают собственную выплату.

## Outbox

Telegram-доставка выполняется как минимум один раз. При недоступности Telegram
события повторяются с увеличивающейся задержкой. `dead>0` в `/health` требует
разбора причины. Для объявления задания скаут видит `в очереди / доставлено /
ошибка` и после исправления возвращает dead-событие кнопкой в очередь. Бизнес-транзакция при
этом остаётся сохранённой; Telegram не является источником истины.

После успешной доставки `group_task` сохраняются фактические `message_id` и
`message_thread_id` ответа Telegram. Только admin API строит по ним private
message link; кнопка «Открыть сообщение в OPS» появляется лишь для `sent`.
При fallback из темы сохраняется фактический thread ответа, а не ожидаемый ID.

Для многочастной публикации есть редкое окно: Telegram уже принял `sendMessage`,
но процесс завершился до записи `message_id`. Повтор может создать дубль — это
честный контракт at-least-once, потому что Bot API не принимает idempotency key.
Старые сообщения удаляются отдельной долговечной очередью; после 10 ошибок задача
переходит в `cleanup_failed`, администраторы получают предупреждение, новая
активная публикация не удаляется и следующие публикации не блокируются.

Входящие updates также доставляются как минимум один раз. Dead update после
исправления причины возвращается через админский redrive с уникальным
`operation_id`; зашифрованный payload доступен для redrive 7 дней. Самовольное
редактирование таблицы inbox запрещено.

Для ускоренной проверки retry разрешено выставить
`BIBITASKS_ENVIRONMENT=staging` и уменьшить `TELEGRAM_RETRY_*`. Production
fail-closed принимает только базу 2 секунды, максимум 3600 секунд и 10 попыток.

## Аналитика и приватность

`product_events` содержит только переходы воронки и перечисляемые признаки.
Туда запрещено записывать имена, username, телефоны, города свободным текстом,
адреса, комментарии, фото, IP, user-agent, initData и токены. Технические
события запуска и каталога хранятся 30 дней, остальные события пилотной воронки
— 90 дней. Очистку выполняет background worker.
Связь с Telegram ID удаляется, когда у субъекта не остаётся событий. Полный
зашифрованный ID получателя удаляется через `WITHDRAW_ACCOUNT_RETENTION_DAYS`
после завершения заявки; маска, fingerprint и финансовый аудит сохраняются.
Срок хранения резервных копий не должен превышать утверждённый срок хранения
рабочих данных.
