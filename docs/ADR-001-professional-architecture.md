# ADR-001: профессиональная архитектура БибиЗадач

Статус: принято, 2026-07-27.

## Решение

Целевая версия — модульный монолит в одном регионе:

```text
Telegram / Mini App
        |
  HTTPS load balancer
        |
  Web API (2+ replicas) ---- private object storage
        |
  managed PostgreSQL
        |
  bot worker + job worker
        |
  transactional outbox -> Telegram
```

## Что уже реализовано в пилоте v2.9

- единая assignment-модель для одноразовых и массовых заданий;
- assignment-bound выплаты и снимок награды на момент взятия;
- release, cancel, expiry и явные переходы approve/revise/reject;
- SQLite transactional outbox с повторной доставкой и dead-letter состоянием;
- зашифрованный ID аккаунта для переводов и внешний номер операции;
- обезличенный журнал продуктовой воронки с retention.
- HTTPS webhook-режим с независимыми route/header secrets, проверкой
  `getWebhookInfo` и durable inbox по `update_id`; polling сохранён для разработки.
- media registry/state machine, private local/S3 adapter, checksum verification,
  proxy signed URL и orphan GC; сетевой upload вынесен из бизнес-транзакций.

Эти механизмы проверяют доменные инварианты до миграции инфраструктуры. Они не
отменяют необходимость PostgreSQL и полного repository cutover для нескольких
экземпляров приложения. S3 backend уже доступен, но SQLite всё ещё ограничивает
runtime одним экземпляром.

Это даёт профессиональную надёжность без преждевременных микросервисов. SQLite-сборка остаётся переходным вариантом для малого пилота на одном экземпляре.

## Неподвижные правила

- Только ledger-модуль меняет баланс.
- Любое начисление имеет уникальный idempotency key.
- Оплата задания привязана к `assignment_id`, а не только к `task_id`.
- Финансовые записи не удаляются; исправление — обратная проводка.
- Создатель финансовой операции не подтверждает её сам.
- Telegram updates дедуплицируются по `update_id`.
- Уведомления и публикации создаются в transactional outbox вместе с бизнес-событием.
- Фотографии хранятся приватно, очищаются от EXIF и выдаются короткими signed URL.
- Все изменения схемы выполняются версионированными миграциями.

## Этапы

1. Защитить пилот: атомарный первый вход, идемпотентные операции, лимиты, фотоотчёт, запрет общего админ-пароля.
2. Разделить домены: identity, workforce, ledger, media, community, notifications.
3. Перенести данные в PostgreSQL с сохранением legacy ID и полной финансовой сверкой.
4. Выполнить resumable backfill legacy-фото в уже реализованный S3-compatible
   private storage и проверить manifest/checksum.
5. Перенести уже реализованные webhook, durable inbox и outbox из SQLite в
   PostgreSQL; polling оставить только для локальной разработки.
6. Запустить минимум два web-процесса, отдельные bot/job workers, метрики, алерты и проверенные backup/restore.

## Критерии production

- 100 параллельных первых входов без 500.
- 10 повторов одного operation ID создают одну проводку.
- Повтор Telegram update не меняет состояние.
- Одно выполнение оплачивается только один раз.
- Фото недоступно постороннему пользователю.
- Потеря Telegram-соединения приводит к retry, а не потере события.
- Есть серверный поиск и пагинация людей.
- Все административные действия видны в audit log.
- RPO не хуже 15 минут, RTO не хуже 60 минут; восстановление проверено отдельно.
